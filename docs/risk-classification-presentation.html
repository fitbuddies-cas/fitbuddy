AI-Risiko-Klassifikation: Produkt & Entwicklungsprozess

Wir haben den AI-Agent-Risiko-Rechner zweimal ausgefüllt: einmal für das Produkt (die FitBuddy-App mit ihrer Claude-Analyse) und einmal für unseren Entwicklungsprozess (Claude Code als Coding-Agent). Beide landen auf Critical — aus unterschiedlichen Gründen, mit unterschiedlichen Massnahmen.

Produkt · App CRITICAL
Entwicklungsprozess CRITICAL

Gate für beide: Explizites Sign-off + Human-in-the-Loop. Red-Line-Checks können nicht gelockert werden — eine Ausnahme ist eine Entscheidung mit Namen dran, keine Konfigurationsänderung.

Einstufung

Vier Achsen, je Stufe 1–4. Pro Achse gilt die höchste Stufe, die ehrlich zutrifft. Basis-Level = höchste Achse; Kombinationen erhöhen; Red Lines übersteuern die Arithmetik.

Produkt — FitBuddy App

User-Trainingsdaten → Claude API → Trainingsempfehlung als Text

Surface Uses knowledge sources 2

Claude erhält aufbereitete Hevy-Daten als Kontext — keine Tools.

Data Special category 4

Trainingsdaten sind Gesundheitsdaten (nDSG Art. 5 lit. c). Zahlungsdaten: keine.

Autonomy Generates text only 2

Nur Text-Empfehlung auf Knopfdruck. Kein Tool-Use, kein Write-back (US-12 = Won't).

Exposure Multiple boundaries 4

Daten verlassen das Gerät zu zwei externen Empfängern: Hevy und Anthropic (USA).

Herleitung Basis-Level 3 (höchste Achse = 3) → Kombination «sensible Daten × verlassen unsere Jurisdiktion» (+1) → Level 4.
Red Line → Critical Besondere Kategorien von Daten (Gesundheitsdaten) gehen an ein Modell ausserhalb der Kontrolle der Organisation — übersteuert die Arithmetik.

Entwicklungsprozess — Claude Code

Coding-Agent mit Schreibzugriff auf Repo, Shell und GitHub

Surface Verändernde Tools 4

Editiert Dateien, führt Shell-Befehle aus, erstellt Branches und PRs.

Data Vertraulich / Secrets 3

Quellcode, interne Doku — und potenziell API-Keys auf der Entwicklermaschine.

Autonomy Plans and executes 4

Plant eigene Schritt-Sequenzen und führt sie aus — verkettete Tools bis zum Ziel.

Exposure Multiple boundaries 4

Kontext geht an Anthropic (USA); Code geht zu GitHub; Tools erreichen weitere Dienste.

Herleitung Basis-Level 4 (höchste Achse = 4): autonomer Agent × zustandsverändernde Tools × Daten verlassen unsere Jurisdiktion.
Einstufung → Critical Ein Agent, der eigenständig plant und mit verändernden Tools auf vertraulichen Daten arbeitet, erreicht das höchste Tier — der Prozess braucht dieselben Gates wie das Produkt.

Always on — nie abschaltbar

Diese Kontrollen gelten auf Tier Critical immer, in beiden Kontexten.

Prompt-Injection- & Jailbreak-ErkennungFremder Input (Hevy-Daten, Web-Inhalte) wird nie als Anweisung behandelt
Harmful-Content-FilterKeine schädlichen Empfehlungen — FitBuddy ist kein medizinisches Produkt
Schutz der System-InstructionsPrompt und Tool-Namen sind nicht durch User-Input überschreibbar
AI-OffenlegungUser weiss immer, dass er mit AI-Output interagiert (EU AI Act, Art. 50)

Massnahmen

Was aus den geforderten Kontrollen bereits umgesetzt ist — und was wir als nächstes angehen. Status: Stand 05.08.2026.

Produkt — App (v0)

Kontrollen aus dem Rechner → konkrete Umsetzung

  • Umgesetzt Human-in-the-Loop Analyse nur auf Knopfdruck (US-3); Umsetzung jeder Empfehlung liegt beim User (Consent, US-4 AC4)
  • Umgesetzt AI-Offenlegung & informierte Einwilligung Consent-Screen vor App-Zugang, Datenschutzerklärung aus Onboarding + Einstellungen
  • Umgesetzt BYO-Key, Keys nur im Keychain ThisDeviceOnly, kein Backend, kein Team-Key (ADR-003/004)
  • Umgesetzt Least Privilege: Hevy nur lesend Kein Write-back — US-12 ist Won't; der Connector hat keine schreibenden Methoden
  • Umgesetzt Rechtsgrundlage USA-Transfer User-eigener Anthropic-DPA inkl. SCCs + Swiss Addendum (ADR-005)
  • Umgesetzt Risikonotiz dokumentiert docs/RISK-CLASSIFICATION.md (PR #63) — die für v0 geforderte Risk Note
  • Offen Certificate Pinning für Hevy + Claude API Als NFR identifiziert, noch zu ergänzen und umzusetzen
  • Offen Kill-Switch-Äquivalent Delete/Reset in der App + dokumentierter Weg: Key in der Anthropic/Hevy-Konsole widerrufen

Entwicklungsprozess — Claude Code

Der Mensch bleibt das Gate vor jedem Merge

  • Umgesetzt Kein Direkt-Commit auf main/develop Pre-Commit-Hook blockt (PR #51); alles läuft über PRs mit min. 1 Review
  • Umgesetzt Human Review jedes AI-Diffs Review-Pflicht vor Merge; Claude-Pre-Review (/code-review) bei grösseren PRs
  • Umgesetzt Leitplanken in CLAUDE.md Konventionen, geprüfte Architektur-Entscheide und Scope-Regeln steuern den Agenten
  • Umgesetzt Tests als Pass/Fail-Gate Unit-Test-Pflicht für ViewModels/Services; Build + Tests vor jedem Commit
  • Umgesetzt Gestufte Releases develop → main nur 1× wöchentlich als gebündelter, reviewter PR
  • Offen Secrets konsequent aus dem Agent-Kontext halten Echte API-Keys nie in Dateien im Repo-Baum; .gitignore-Abdeckung prüfen
  • Offen Permission-Regeln schärfen Destruktive Befehle (push, delete) nur mit expliziter Bestätigung — kein Blanko-Auto-Approve
  • Offen Named Owner + Sign-off Pro Release eine benannte Person, die das Go-Live explizit freigibt

Warum Critical kein Blocker ist: Beim Produkt folgt das Tier direkt aus der Red Line «Gesundheitsdaten an ein externes Modell» — das ist der Kern des Produkts selbst, nicht ein vermeidbarer Implementierungsfehler. Beim Entwicklungsprozess folgt es aus der Natur eines Coding-Agenten. In beiden Fällen lautet die Antwort nicht «abschalten», sondern: Human-in-the-Loop an jeder Stelle, an der etwas Wirkung entfaltet — der User entscheidet über jede Trainingsempfehlung, das Team über jeden Merge.

Verantwortlichkeiten auf diesem Tier: Security-Review vor dem Merge · benannter Owner · Pass/Fail-Test vor Go-Live · Kill-Switch verifiziert · explizites Security-Sign-off vor Go-Live · alles dokumentiert, geloggt, zuordenbar.
